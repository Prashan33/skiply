## Prompt

> Implement the intelligent search. Connect the Sanity Context MCP, the server-side
> search API, and the result page (video and lesson results) over courses and lessons.
> @design/vertex-search.png

---

## Goal

Ship the end-to-end search experience for Vertex/Skiply:

1. **Sanity Context MCP** wiring — a `sanity.agentContext` config document (groqFilter +
   instructions) plus the env/URL plumbing.
2. **Server-side search API** — `app/api/search/route.ts`. Connects to the Sanity Context
   MCP over server-side HTTP, injects the cached initial schema context + an inline system
   prompt, calls the LLM (OpenAI `gpt-4.1` via the Vercel AI SDK) with the MCP GROQ tools,
   and returns a **grounded, structured** result payload validated by Zod. Streams if the
   AI-SDK structured-output streaming cooperates; otherwise returns JSON in one shot.
3. **Results page** — `app/search/page.tsx` + client components reproducing
   `design/vertex-search.png`: header ("Results for "<query>"", "Found N results across M
   courses"), the search input, `N results` count + a "Most Relevant" sort control, a
   ranked list of **VIDEO** and **LESSON** result cards, an empty state, and the bottom
   "Can't find what you're looking for? / Browse all courses" CTA.

Scope is **courses and lessons only**. `instructor`, `category`, and `video` documents are
context for the agent, never surfaced as results.

### Explicitly out of scope (separate AGENTS.md items)

- **Real video-moment matching / "Watch from MM:SS".** `video` docs have empty
  `chapters`/`chunks` and there is no ingestion pipeline yet (AGENTS §9). Per the decision
  below, VIDEO cards ship now but are driven by lesson-topic matches and deep-link to the
  lesson video at `0:00` — no fabricated second. `startSeconds` stays in the schema for the
  pipeline to populate later.
- Conversation Insights / telemetry classification (AGENTS create-agent skill step 3).
- Per-learner progress (the completion check shown on the design's LESSON card is a
  presentational placeholder, consistent with `CourseProgressBar` / `LessonSidebar`).
- Semantic search (`text::semanticSimilarity()`) — embeddings are a billing decision
  (AGENTS §12); keyword match with wildcards only.

## Decisions & assumptions

### A. Sanity Context MCP configuration

1. **`groqFilter`:** `_type in ["course", "lesson"]`. Keeps the agent off `video`,
   `instructor`, `category`, and any future system types. (The agent may still *read*
   `video`/`instructor`/`category` when it needs a name or icon only if we widen this later;
   for this task the scope stays courses + lessons, matching the request.)
2. **Instructions field content** (pure deltas — see `dial-your-context`; kept short):

   ```markdown
   ### Scope
   - Only `course` and `lesson` are in scope. Never present `video`, `instructor`, or
     `category` documents as results.

   ### Schema notes
   - `lesson` does not store its course. Resolve it with
     `*[_type == "course" && references(^._id)][0]`.
   - "Module N" and "Lesson N.M" are NOT stored — they come from the order of
     `course.modules[]` and `module.lessons[]`. You do not need to compute them; return the
     lesson `slug.current` and the app derives the labels.
   - `lesson.notes` is Portable Text. Never match it directly — match `pt::text(notes)`.

   ### Query rules
   - Text match is token-based. Wildcard every keyword (`*term*`) and OR the terms:
     `title match "*data*" || title match "*fetch*" || pt::text(notes) match "*data*"`.
     Never match a whole phrase as one pattern.
   - Return every relevant lesson, ranked best-first. Do not cap the list.
   - Rank by specificity: the concept in the lesson `title` beats the concept in `notes`,
     which beats a broad keyword hit.

   ### Video moments
   - Transcript/chapter data is not available yet: every `video` doc has empty `chapters`
     and `chunks`. Do not attempt timestamp matching. Return `startSeconds: 0`.
   ```
3. **Delivery:** the `@sanity/context` Studio plugin is not installed (and may lag the
   Studio Sanity major — AGENTS §6/§12). So the config doc is **not** a Studio schema type
   (Sanity reserves the `sanity.` type namespace; a custom `sanity.agentContext` type can't
   be registered). Instead ship an **import file**
   `studio/scripts/seed/agent-context.ndjson` with one document:

   ```json
   {"_id":"agentContext.vertex-search","_type":"sanity.agentContext","slug":{"_type":"slug","current":"vertex-search"},"title":"Vertex search","groqFilter":"_type in [\"course\", \"lesson\"]","instructions":"<the block above>"}
   ```

   The user imports it (`cd studio && npx sanity dataset import scripts/seed/agent-context.ndjson production --replace`) and deploys the Studio. Until then the route falls back to the **base** MCP URL (no slug) and relies on the inline system prompt + `?groqFilter=` URL param.
4. **MCP URL / env:** add to `.env.example` (and the user sets real values in `.env.local`):
   - `OPENAI_API_KEY=` — **server only**.
   - `SANITY_CONTEXT_MCP_URL="https://api.sanity.io/v2026-03-03/context/mcp/g178ibto/production"`
     — base URL now; the user appends `/vertex-search` after importing the config doc.
   - Bearer auth reuses `SANITY_API_READ_TOKEN` (already server-only).
   - If `SANITY_CONTEXT_MCP_URL` has no `/…/<slug>` segment, the route appends
     `?groqFilter=_type%20in%20%5B%22course%22%2C%22lesson%22%5D` so scope holds even before
     the doc is imported.

### B. Server route — `app/api/search/route.ts`

5. **Shape:** `export const runtime = "nodejs"`, `export const maxDuration = 30`. `POST`
   only; body `{ query: string }` (Zod-parsed, trimmed, 1–200 chars, else `400`).
6. **Startup, once per module (cached):**
   - `fetchInitialContext()` — `GET ${MCP_URL}/initial-context` with
     `Authorization: Bearer ${SANITY_API_READ_TOKEN}`, response text cached in a
     module-scope `let`. On failure, log and continue with an empty string (agent can still
     call `schema_explorer`). Document the AGENTS §12 caveat: once cached, changing the
     system prompt or the initial context needs a **server restart**.
7. **Per request:**
   - `Promise.all([ createMcpClient(), fetchInitialContext() ])`.
   - `const mcpTools = await mcpClient.tools()`; drop `initial_context`
     (`const { initial_context: _omit, ...tools } = mcpTools`).
   - LLM call with **structured output + tools**. Preferred:
     `streamText({ model: openai("gpt-4.1"), system, prompt: query, tools,
     stopWhen: stepCountIs(8), experimental_output: Output.object({ schema:
     searchResponseSchema }) })`, returned via the AI-SDK streaming-response helper that
     pairs with `experimental_useObject` on the client. **Fallback** (if partial-object
     streaming is fiddly with this AI-SDK version): `generateText({ ... , experimental_output
     })` then `return Response.json(result.experimental_output)`; the client does a plain
     `fetch` + `setState`. Ship whichever works cleanly and record it in the Result section.
   - `await mcpClient.close()` in `finally` / `onFinish`.
   - Wrap the whole handler in try/catch → on any failure return
     `Response.json({ error: "search_unavailable" }, { status: 503 })` so the UI can show a
     friendly state (common cause: Studio not deployed yet, or `OPENAI_API_KEY` unset).
8. **Inline system prompt** — a template literal with **escaped backticks** (AGENTS §12).
   Contains, mirroring the Instructions field (AGENTS §11 "critical rules in both"):
   - Role: "You search a learning catalog and return ranked, grounded result cards. You are
     not a chatbot — you only emit the structured object."
   - Grounding: never invent a course, lesson, slug, count, or timestamp. Only emit
     `lessonSlug` values that appeared in your GROQ query results. If nothing matches,
     return `{ "results": [] }`.
   - Scope: courses and lessons only.
   - The token-based match rules + specificity ranking (verbatim from the Instructions
     block).
   - Result kinds: default `kind:"lesson"`; use `kind:"video"` when the lesson's primary
     value is watching the video walkthrough/demo (heuristic from title/notes — real
     moment-matching is pending the ingestion pipeline). Both kinds link to the lesson page.
   - `description`: one or two plain sentences, grounded only in that lesson's own
     title/notes/keyPoints, no markdown, ≤ 240 chars.
   - `startSeconds`: always `0` for now.
   - Then: `\n\n## Schema context\n` + the cached initial context.
9. **No Conversation Insights / telemetry integration** in this task (noted in scope).

### C. Shared contract — `lib/search.ts` (pure, no `server-only`)

10. Zod schema + inferred types, imported by both the route (server) and the client
    component:
    ```ts
    export const searchResultSchema = z.object({
      kind: z.enum(["video", "lesson"]),
      lessonSlug: z.string(),          // must exist in the index; client drops unknowns
      description: z.string().max(240),
      startSeconds: z.number().int().min(0).default(0),
      relevance: z.number().min(0).max(1),
    });
    export const searchResponseSchema = z.object({ results: z.array(searchResultSchema) });
    export type SearchResult = z.infer<typeof searchResultSchema>;
    ```

### D. Grounding the display — server-built lesson index (not from the model)

11. Everything the cards show except `kind` / `description` / `startSeconds` is **derived on
    the server from Sanity**, keyed by `lessonSlug`, so labels/counts can't be hallucinated
    (AGENTS §7, §8, §11):
    - New GROQ `SEARCH_INDEX_QUERY` in `sanity/lib/queries.ts`:
      ```
      *[_type == "course" && defined(slug.current)] | order(title asc) {
        "courseTitle": title,
        "courseSlug": slug.current,
        modules[]{
          title,
          "lessons": lessons[]->{
            "lessonSlug": slug.current,
            "lessonTitle": title,
            duration,
            keyPoints,
            "poster": coalesce(poster, thumbnail){ asset }
          }
        }
      }
      ```
    - New `getSearchIndex()` in `sanity/lib/fetch.ts`:
      `getReadClient().fetch(SEARCH_INDEX_QUERY, {}, { next: { revalidate: 300, tags:
      ["course", "lesson"] } })`.
    - `app/search/page.tsx` (server) flattens the result into
      `Record<lessonSlug, SearchIndexLesson>` where
      ```ts
      type SearchIndexLesson = {
        lessonSlug: string; lessonTitle: string;
        lessonLabel: string;   // "Lesson 5.1"  (moduleIdx+1 . lessonIdx+1)
        moduleLabel: string;   // "Module 5"
        moduleTitle: string;   // "Data Fetching & Caching"
        courseTitle: string; courseSlug: string; courseMonogram: string;
        keyPoints: string[]; durationClock: string;  // "12:45"
        posterUrl: string | null;                    // urlFor(poster).width(320).height(180).fit("crop").url()
      };
      ```
      and passes it to the client component as a prop.

### E. Results page — `app/search/page.tsx` + `components/search/*`

12. **`app/search/page.tsx`** (server): `<TopNav showActions />` + `<Container as="main">`,

    `search_page_viewed` mirrors the course/lesson pages (guarded `getPostHogClient()` +
    `flush()`), with `{ query: q ?? null }`.
13. **`components/search/SearchResults.tsx`** (`"use client"`): owns the query state,
    the search input, the fetch, the sort control, and rendering.
    - Input: reuse `<Input icon shortcut="⌘K" />` inside a `<form>`; submit →
      `router.replace(`/search?q=${encodeURIComponent(value)}`)` (shallow, keeps history
      tidy) **and** runs the search. Runs once on mount if `initialQuery` is non-empty.
    - Search call: preferred `experimental_useObject({ api: "/api/search", schema:
      searchResponseSchema })` → progressive partial `results`; fallback plain
      `fetch("/api/search", { method:"POST", body: JSON.stringify({ query }) })`.
    - **Grounding guard:** map streamed/returned `results` through the `index`; **drop any
      whose `lessonSlug` is not in the index**. Each surviving result →
      `{ ...modelResult, ...index[lessonSlug] }`.
    - Header block (matches the design): orange uppercase eyebrow "SEARCH RESULTS";
      `font-display` H1 `Results for ` + the query in `text-primary-500` wrapped in typographic
      quotes; sub-line `Found ${count} result${s} across ${courseCount} course${s}` where
      `count = grounded.length` and `courseCount = new Set(grounded.map(r =>
      r.courseSlug)).size` — **both derived, never from the model**.
    - Toolbar row: left `${count} results`; right a `<Select>` — options **Most Relevant**

    - Bottom CTA bar always rendered under the list: "Can't find what you're looking for? /
      Try different keywords or browse our full course catalog." + `<Button>` link

## Security considerations

- `SANITY_API_READ_TOKEN` and `OPENAI_API_KEY` are read **only** in
  `app/api/search/route.ts` (Node runtime, `server-only` transitively via `sanity/lib`).
  Never passed to a client component, never in a response body. `.env.example` updated;
  real values only in `.env.local` (git-ignored).
- The browser calls **only** `/api/search` (same origin). It never contacts
  `api.sanity.io/context`, the MCP, or OpenAI. No token in `NEXT_PUBLIC_*`.
- The route is read-only: MCP `groq_query` / `schema_explorer` against a
  `_type in ["course","lesson"]` filter. No write tool, no mutation, no progress write.
- Input validation: `query` Zod-checked (type, trim, 1–200 chars) before use. The model
  output is Zod-validated; unknown `lessonSlug`s are dropped client-side against the Sanity
  index (defence in depth against a hallucinated slug reaching a link).
- `description` is rendered as **plain text** (no `dangerouslySetInnerHTML`, no markdown/
  HTML parsing) — a hostile string can't inject markup.
- Result links are internal (`/lessons/<slug>`) only; `slug` is URL-encoded and matched
  against the index, so no open-redirect / path-injection surface.
- Never send a transcript or `chunks` array to the model (AGENTS §12) — the groqFilter
  excludes `video`, and the instructions forbid transcript queries.
- MCP client is always closed (`finally`) so a failed request can't leak a socket.

  `/vertex-search` once the config doc is imported so the stored `groqFilter` +
  `instructions` apply.
- **After the config doc is live**, changes to its `instructions` take effect on the next
  request, but changes to the **inline system prompt** or the cached initial context need a
  **server restart** (AGENTS §12).
- **VIDEO results are a heuristic, not true moment matching.** `startSeconds` is always `0`
  and the action reads "Watch lesson" until the transcript/chapter ingestion pipeline
  (AGENTS §9) lands and populates `video.chapters` / `video.chunks`. At that point:

  return real `startSeconds`, and the card label becomes "Watch from MM:SS".

  `CourseProgressBar` / `LessonSidebar`) — real per-learner progress is a separate task.
- **Streaming vs one-shot:** the route ships whichever of AI-SDK streamed structured output

  the requirements.
- **Schema ↔ seed drift** (pre-existing): lesson image is `thumbnail` not `poster`;

  follow-up re-seed, not fixed here.
- **`groqFilter` scope:** set to `_type in ["course","lesson"]` per the request. If you
  later want the agent to read instructor/category names for richer cards, widen it and
